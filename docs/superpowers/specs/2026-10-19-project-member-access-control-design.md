- 日期：2026-10-19

- 目标仓库：[CorlyDream/label-studio](https://github.com/CorlyDream/label-studio)，目标分支：`develop`。
- 源码基线：[`d9a213ccf748c253dfcb3d359e8d3fd2c3da068d`](https://github.com/CorlyDream/label-studio/commit/d9a213ccf748c253dfcb3d359e8d3fd2c3da068d)。该基线与方案讨论时检查的上游提交一致。
- 适用范围：自部署 Label Studio Community Edition，在现有组织、账号和项目模型上增加项目级访问控制。

## 1. 背景与目标

当前需要的工作流程是：项目创建者建立项目，选定可以参与的用户；这些用户登录后，只能查看获授权的项目及数据，并在其中完成标注；创建者可以取消授权。

社区版官方文档说明，同一实例中的用户拥有相同功能并能看到全部项目。官方 Starter Cloud 和 Enterprise 已提供项目成员及角色权限，但本设计选择继续维护自部署社区版。[D1] [D2]

本设计的成功标准：

1. 项目列表、搜索、分页、数量统计及辅助信息只包含当前用户有权访问的项目。
2. 未授权用户即使知道项目、任务、标注、图片或导出文件的地址，也不能通过受保护的服务入口读取或修改资源。
3. 授权成员可以完成正常标注，但不能修改项目设置、管理成员、导入导出或删除任务。
4. 项目创建者可以管理自己负责的项目，组织负责人可以管理本组织项目。
5. 取消授权后，后续服务端鉴权按照最新成员关系执行；历史标注及作者信息保留。
6. 浏览器会话、个人 API Token 和 SDK 使用相同的项目权限规则。

## 2. 范围与设计选择

采用“复用项目成员表 + 固定访问/管理规则 + 统一查询范围”的方案。项目授权控制谁能进入项目，继续使用已有任务队列、标注编辑器、账号和登录机制。

第一版将上一轮方案具体化为以下默认行为：组织负责人统一创建新项目；项目创建者管理自己的项目；被授权用户负责标注。已有的非组织负责人项目创建者继续拥有对应项目的管理权限。创建权限是明确的组织级规则，不额外引入 Manager 角色。

第一版不包含用户组、角色/权限配置表、工作空间继承、逐任务派单、审核员流程、共识计算、多个项目管理员、项目所有权转移、SSO 或公开项目模式。暂不引入 Casbin、django-guardian 等额外权限依赖，也不增加可将权限整体切回全员开放的运行时开关。

本次仅在目标仓库保存设计文档。实现时遵循仓库类型标注、必要注释和测试约定；新方法和类应说明职责及权限边界。[R1]

## 4. 权限语义

### 4.1 必须先成立的组织边界

对于任意用户和项目，以下条件必须全部成立后，才能判断创建者或成员权限：

- 用户已通过现有认证，且账号有效。
- `user.active_organization_id == project.organization_id`，两者均非空。
- 用户在该组织内存在有效的 `OrganizationMember`，且没有被移除或软删除。
- 项目处于现有项目查询允许访问的状态；已删除项目不能因成员授权重新出现。

组织边界不成立时，项目创建者身份、组织负责人身份及残留的项目成员记录均不产生访问权限。保留现有项目/任务状态与锁定规则，项目授权不自动放宽它们。

### 4.2 管理者与普通成员

组织边界成立后，按以下固定规则判断：

- 组织负责人：`Organization.created_by_id == user.id`，可管理该组织内项目。
- 项目创建者：`Project.created_by_id == user.id`，可管理该项目。
- 普通项目成员：存在 `(project, user)` 对应且 `enabled=True` 的 `ProjectMember`，可访问并参与标注。
- 无上述身份：不能访问项目。

管理者隐式拥有访问和标注能力，不依赖 `ProjectMember` 行。禁用创建者或组织负责人的成员行不会撤销其隐式管理权限；成员页面应明确展示这些身份，且不提供无效的“取消管理权限”操作。组织移除会撤销其组织范围内访问；所有权转移不在第一版范围内。

不新增全局 `User.role`。同一个用户可以管理项目 A，并作为普通成员标注项目 B。`is_staff`、`is_superuser` 和当前恒真的 `is_organization_admin()` 均不单独赋予应用 API 的项目权限。Django admin 只向有效组织负责人中的可信后台账号开放，普通标注账号不得通过后台绕过应用规则；服务器、数据库和部署管理员属于受信任运维边界。

### 4.3 固定操作矩阵

本表均以目标项目在当前组织边界内为前提。“管理者”指该项目创建者或组织负责人。

| 操作 | 管理者 | 启用的普通成员 | 未授权用户 |
| --- | --- | --- | --- |
| 查看项目、任务、图片、预测结果及所有已提交标注 | 允许 | 允许 | 拒绝 |
| 正常提交标注、跳过任务、使用标注队列和任务锁 | 允许 | 允许 | 拒绝 |
| 使用已配置后端进行当前任务的交互式预测 | 允许 | 允许 | 拒绝 |
| 修改/删除自己的已提交标注 | 允许 | 允许 | 拒绝 |
| 修改/删除其他人的已提交标注 | 允许 | 拒绝 | 拒绝 |
| 查看、保存、转换、修改、删除草稿 | 仅本人草稿 | 仅本人草稿 | 拒绝 |
| 修改项目设置、标签配置和成员 | 允许 | 拒绝 | 拒绝 |
| 创建/修改/删除任务、导入、导出及下载导出文件 | 允许 | 拒绝 | 拒绝 |
| 存储配置/同步、ML 配置/训练/测试、预测管理、Webhook 管理 | 允许 | 拒绝 | 拒绝 |
| 持久化共享 Data Manager 视图及执行批量写操作 | 允许 | 拒绝 | 拒绝 |
| 删除项目 | 允许 | 拒绝 | 拒绝 |

新建项目、组织邀请链接查看/重置、组织成员管理和账号管理属于组织级操作，第一版仅允许有效组织负责人执行。项目创建者只能通过受限用户选择接口为自己的项目添加已有组织成员；普通用户可以访问和修改自己允许修改的账号资料，不能修改其他用户资料或任何权限身份字段。

### 4.4 标注、草稿与归属字段

普通标注创建请求的作者固定为当前用户；提交不同的 `completed_by` 应拒绝，不能借此冒用身份。常规标注更新不修改原作者，管理者修改他人结果也保留原作者。管理者导入历史标注可以沿用现有作者映射及组织归属校验，但导入作者不自动获得项目成员资格。[S7] [S14]

草稿记录、内容及与个人草稿有关的响应字段仅对草稿所属用户开放，管理者没有读取他人草稿的例外。检查普通列表、详情、任务嵌套响应和草稿转标注路径；用户可见的草稿计数/草稿标签字段按本人过滤，不引入新的聚合系统。具有管理权限的任务/项目删除仍可按现有外键关系清理关联草稿，但不能借清理接口返回草稿内容。

草稿绑定已有标注时，除校验同一任务外，还应检查当前用户是否有权修改该标注。草稿转换必须同时满足草稿属于本人、属于当前任务和目标标注写权限。

常规项目创建由服务器固定 `created_by` 和 `organization`；普通更新不得改动它们。子资源创建以已授权的 URL/业务父对象为准，请求中的任务、项目、标注、预测或草稿引用必须与之匹配，即使用户同时能访问两个项目也不能混用。更新保留现有不可变父字段的忽略语义时，必须保证持久化归属完全不变；新增接口应显式拒绝重新归属请求。校验失败发生在任何持久化或外部副作用之前。

## 5. 数据模型与授权生命周期

复用 `ProjectMember`，不新增角色列。新增数据库唯一约束 `(project_id, user_id)`，兼容 SQLite 和 PostgreSQL。授权操作通过唯一约束和事务保证并发安全，成员查询在数据库中完成，不能逐项目读取后在 Python 中过滤。

- 授权：目标用户必须是有效的同组织成员；创建成员行或将已有行更新为 `enabled=True`。
- 取消授权：将已有行更新为 `enabled=False`；不存在的行按已取消处理。
- 重复操作：重复授权不创建重复行，重复取消不报错。
- 保留历史：取消授权不删除用户、任务、已提交标注、作者信息或个人草稿；用户再次获授权后可继续访问仍存在的本人草稿。
- 组织移除：同时禁用该用户在该组织下的显式项目成员行，释放现有任务锁；组织边界检查独立生效。再次加入组织不会自动恢复旧的显式项目授权。若其仍是项目创建者，重新成为有效组织成员后恢复相应隐式权限。
- 账号暂停：账号无效期间全部拒绝；恢复账号后按当时组织成员关系、项目成员状态和隐式身份重新判断。

权限判断读取当前数据库状态。第一版不引入跨请求的成员缓存；同一请求内可以复用已解析的项目和权限结果。组织成员及项目成员均有效才构成普通成员授权，不能把不存在、禁用或异常状态解释成全员开放。

## 6. 后端接入与模块边界

### 6.1 单一规则来源

新增集中且职责明确的权限模块，例如 `label_studio/projects/access.py`，提供以下契约：

| 契约 | 职责 |
| --- | --- |
| `visible_projects(user)` | 返回符合组织边界及项目授权规则的 queryset |
| `can_access_project(user, project)` | 对单个项目判断查看及正常标注能力 |
| `can_manage_project(user, project)` | 对单个项目判断管理能力 |
| `can_create_project(user)` | 判断当前有效组织负责人身份 |

列表查询与对象判断应共享相同条件，避免重复实现不一致的管理员或 `enabled` 语义。`Project.has_permission(user)` 委托项目访问判断；动作授权在明确解析目标对象/父项目后调用相应管理或标注规则。对外入口使用用户范围查询，迁移和受信任系统作业保留无用户内部查询能力，不能让公开请求落入无用户放行分支。

### 6.2 显式执行动作权限

在 DRF 默认权限链或项目资源的通用 API/mixin 中实际执行动作权限，复用已存在的权限名称和 `permission_required` 声明作为映射输入，但必须验证其运行时消费路径。权限模块不依赖当前对已登录用户普遍放行的 `user.has_perm()` 作为项目管理依据。

动作按业务含义映射，不能按 HTTP 方法简单推断：读取存储配置、导出文件下载属于管理动作；某些用于过滤或交互式预测的 POST 属于正常标注动作。标准详情检查、列表过滤、无对象创建、自定义 action 和非 DRF 文件视图分别接入。所有项目资源入口，包括读取管理配置的 GET，都必须有明确动作映射；缺失映射默认拒绝，并由接口覆盖测试发现。覆盖显式重写 `permission_classes` 的 API，避免默认权限链接入后仍存在独立放行路径。

### 6.3 必须覆盖的资源入口

| 模块/入口 | 必须落实的行为 |
| --- | --- |
| `projects` 列表、counts、详情、summary、next、history、sample、model versions、annotators | 按项目可见范围读取；管理动作单独检查；辅助成员查询处理 `enabled`，不可泄露其他项目 |
| `TaskManager.for_user()`、任务/标注/草稿/预测 API | 使用项目授权范围；列表不可依赖逐对象权限钩子；写操作执行第 4.4 节作者及归属规则 [S7] [S9] [S14] |
| Data Manager views/state/columns/actions、prepared queryset | 视图与显式项目必须一致；共享视图持久化操作为管理权限；普通成员保留请求内筛选、排序和选择能力 [S8] [S9] |
| Data Manager 批量操作 | 第一版所有批量管理写操作仅管理者可执行；显式 ID 集合先验证全部对象及父项目，不允许“部分成功”或由客户端作者筛选绕过。正常标注队列的 `next_task` 及其必要任务锁按项目访问权限执行，不属于批量管理写操作 [S15] [S24] |
| 导入、上传列表/删除、导出快照、导出下载 | 导入导出均为管理操作，创建作业与下载结果分别鉴权；覆盖 `/api/auth/export/` [S10] [S16] |
| 存储及 ML 管理/验证/同步、Webhook | 授权后才能读取配置、复用凭据、连接外部服务或启动作业；更新不能通过 `project` 字段迁移归属 [S17] [S18] [S19] |
| 用户/组织 API 与当前用户信息 | 自身账号修改和组织管理分开；普通用户不能操作他人或组织管理；对项目贡献列表等辅助字段施加项目过滤 [S11] [S12] [S20] |
| 项目 HTML 页面及原始文件入口 | 禁止服务端模板嵌入未授权项目数据；原始图片、导出下载和代理入口调用同一规则 [S16] [S21] [S22] |

授权失败必须发生在 serializer 校验可能产生的外部连接、凭据传递、保存文件、队列入列、发送变更 Webhook 和更新计数之前。管理者可配置的集成仍属于受信任项目管理面；标注员只能使用已经配置好的交互式能力，响应不得嵌套返回存储密钥、后端认证参数等管理配置。

组织级或未绑定项目的 Webhook/集成仅组织负责人可管理。项目创建者只能管理明确绑定到其有权管理项目的资源，不能通过空项目、修改作用范围或默认组织查询获取组织级配置和其他项目数据。

## 7. 成员 API 与错误约定

### 7.1 成员管理接口

以下接口为新增设计，不表示社区版当前已存在。

| 接口 | 权限及语义 | 成功响应 |
| --- | --- | --- |
| `GET /api/projects/{id}/members/` | 管理者读取隐式管理身份及显式成员；使用现有分页约定 | `200` |
| `GET /api/projects/{id}/members/available/` | 管理者搜索可添加的有效同组织用户；只返回选择所需字段 | `200` |
| `PUT /api/projects/{id}/members/{user_id}/` | 幂等授权/启用一个普通成员，不接受角色或项目归属字段 | `200`，返回成员状态 |
| `DELETE /api/projects/{id}/members/{user_id}/` | 幂等禁用显式普通成员，不删除历史标注 | `204` |

成员信息仅包含用户 ID、展示名、必要邮箱、启用状态、时间及管理身份提示，不复用包含其他项目贡献详情的组织用户响应。隐式管理者在成员列表中标明 `access_source` 为 `organization_owner` 或 `project_creator`，不额外创建成员行；对这些身份执行授权/取消接口返回 `400` 和明确提示，避免误导为可以撤销其管理权。

`members/available/` 复用组织成员查询及现有搜索/分页组件，只为有权管理该项目的用户开放。目标账号无效、不属于该组织或不存在时，统一返回不暴露跨组织身份的 `400` 校验错误。该接口不创建账号、不发邀请、不更改组织角色。

### 7.2 可见范围与错误码

- 未登录：沿用现有认证类的未认证响应及页面登录跳转约定；统一保证不返回项目数据。
- 普通集合查询：剔除无权限对象及其派生统计，不能用过滤前总数分页。
- 请求明确指向不可访问的项目或子对象：返回 `404`，不披露存在性。显式项目过滤的子资源列表也先解析项目；多个明确项目 ID 中有未授权项则整体拒绝。
- 项目可访问但操作不允许：返回 `403`。
- 私有草稿不属于当前用户：列表过滤，详情/修改/删除返回 `404`。
- 参数无效、混用父对象或非法作者：使用现有序列化 `400` 格式；已有不可变字段的更新处理遵循第 4.4 节，新增接口显式拒绝重新归属。无法访问的关联对象仍以不披露信息的方式拒绝。

项目详情及项目列表项新增只读 `access` 字段，至少包含 `can_annotate` 和 `can_manage`。全局当前用户响应只表达组织及账号级能力；项目能力由各项目计算，前端不自行推导。接口字段是 UI 展示信息，不作为后端授权依据。

## 8. 前端体验

在项目设置中增加“项目成员”页，复用现有 `@humansignal/ui`、用户搜索、分页、通知和设置导航。当前社区版设置菜单没有项目成员页面；组织 People 页的邀请功能不能代替项目授权。[S23] [R2]

- 管理者查看隐式管理身份和普通成员，搜索已有组织用户后点击“添加成员”提交；取消授权使用明确按钮和确认提示，不使用容易误触的自动保存配置。
- 普通成员登录后只看到有权访问的项目；无项目时显示“暂无获授权的项目，请联系项目负责人”。
- 根据 `access` 隐藏项目管理、导入导出、删除任务、共享视图编辑和批量写操作，保留标注、本人草稿和请求内筛选。
- 标注界面允许查看已有标注；非本人标注对普通成员只读，禁止通过快捷键或切换选择绕过。
- 已打开页面在后续请求收到权限拒绝时，停止进一步提交，显示“项目不可访问，可能已被删除或访问权限已取消”，提供返回项目列表入口；不宣称本次保存成功，也不自动无限重试。
- 保留未提交编辑内容在当前页面内，供用户联系负责人处理；不新增未授权下载功能。恢复权限后通过重新加载确认服务端状态。

UI 只负责减少误操作；浏览器隐藏按钮不构成权限边界。成员页遵循仓库现有键盘操作、可访问性和设计 token 约定。[R2]

## 9. 图片与导出文件访问

### 9.1 上传与本地文件

上传文件已有委托项目权限的对象钩子，上传原图响应、下载存储数据和 Nginx 转发应保留这条检查链。部署不得通过另一条静态文件路径直接公开私有上传目录。[S16]

当前本地文件授权按有权访问项目的存储目录覆盖判断，而非逐任务文件引用判断。第一版沿用项目存储目录作为边界，敏感项目分别使用独立目录，例如 `/data/project-a/` 与 `/data/project-b/`；不得给某项目配置覆盖其他私有项目图片的共同父目录。[S21]

文件路径必须规范化并进行目录边界检查，沿用并核对现有路径安全辅助函数。配置存储及首次迁移时检查目录重叠；跨权限项目的重叠目录必须调整后才能开放成员访问，不增加逐文件 ACL 表。

### 9.2 云存储与 URI 解析

任务/项目 URI 解析在颁发签名 URL 或代理字节前检查项目访问权限。除项目 ID 外，还要校验所请求对象属于该项目配置的存储范围；对象 key 必须处于获授权的项目 prefix 内，不能借项目 A 的解析入口访问同一 bucket 下项目 B 的对象。[S22]

云存储使用私有访问策略和项目独立前缀/凭据范围。公开 URL 或用户本来就在其他渠道有权读取的对象，不属于应用 ACL 能单独隔离的范围。现有图片引用迁移需核对这一前提。

### 9.3 撤销权限的实际边界

成员禁用事务提交后，才开始进行服务端授权检查的请求必须被拒绝；不要求退出登录或重置个人 Token。已经通过鉴权的在途请求、正在传输的响应、浏览器缓存、已下载内容以及尚未过期的云签名 URL 不承诺回收或中断。

需要每次新图片请求重新鉴权时使用代理模式；使用直连签名 URL 时沿用已配置有效期，并将有效期视为撤销后可能继续访问的时间窗口。第一版不引入签名 URL 撤销服务或全项目写锁。

导出开始、查询导出状态、下载导出结果和 Nginx `auth_request` 均检查当前管理权限。已经进入执行阶段的作业可按现有机制完成，但结果读取仍重新鉴权，不因“作业曾经获准”放行后续下载。

## 10. 存量迁移与部署

首次启用是将全员可见收紧为明确授权，必须有一次受控切换；后续普通升级不得重复清空授权。

1. 固定部署版本并备份数据库、上传文件与存储配置，记录现有项目创建者、组织负责人及成员行。
2. 检查组织负责人有效性；负责人为空或已失效的组织由可信运维先修复。项目创建者为空时，组织负责人作为管理入口，不给任意成员自动接管。
3. 盘点 CLI 创建的 staff/superuser 账号；普通标注账号应收紧为普通身份，Django admin 入口按第 4.2 节保护。后续普通账号创建路径不得继续意外授予后台权限。
4. 在停止对外写入和普通用户访问的维护窗口执行数据迁移：同一 `(project, user)` 保留最小主键记录，`created_at` 取同组最早值、`updated_at` 取同组最晚值，删除其余重复行；历史显式成员一律初始化为 `enabled=False`，不将旧用途的行直接视为已批准授权；再建立唯一约束。
5. 部署完整的列表、对象、动作和媒体权限链。项目创建者及组织负责人通过隐式权限进入旧项目，根据已确认名单显式重新授权。没有成员的项目保持仅管理者可见。
6. 检查本地目录重叠、云存储前缀、公开图片路径、共享管理员 Token 和现有自动化集成。个人标注流使用个人凭据；受信任后台集成由明确有权的管理账号运行，不向标注员暴露凭据。
7. 按第 11 节使用普通账户完成权限验收后恢复普通用户访问。此后授权变更通过成员 API 完成，不再批量禁用历史行。

数据迁移保留全部业务数据和作者归属。回滚到旧社区版代码会重新扩大项目可见范围；技术回滚只能在普通用户入口仍关闭的维护窗口进行，不能将关闭 ACL 当作在线故障降级。

## 11. 验收与回归验证

创建组织负责人 O、历史项目创建者 C、普通用户 A/B、无授权用户 U，以及另一个组织的用户 X；至少包含两个项目、禁用成员、无创建者项目和两个数据库后端。测试权限行为，不将实现细节直接照抄为测试。

| 场景 | 验收结果 |
| --- | --- |
| O 创建项目，A 仅获项目 1，B 仅获项目 2 | 项目列表、搜索、分页、counts 及辅助贡献信息只出现授权范围 |
| A 猜项目 2 的项目/任务/标注/预测 ID | 详情、替代列表、Data Manager、next/history 和展开字段都不泄露项目 2 |
| A 正常提交、跳过、交互预测及编辑本人标注 | 原有标注流程可用，作者始终正确 |
| A 修改他人标注、伪造作者或使用别人的草稿 | 修改他人结果返回 403；他人草稿不可见且不能转换或保存 |
| C/O 读取其他用户的草稿 | 草稿列表/嵌套内容按本人过滤，直接请求返回 404；管理者仍可修改已提交标注 |
| A 请求设置、导入导出、成员管理或批量写操作 | 403；不产生数据、外部连接、队列或变更事件副作用 |
| A 使用共享视图和请求内筛选 | 正常可读可筛选；持久化修改视图、顺序、锁定、重置被拒绝 |
| C/O 使用混合项目 ID、重设子资源父对象或凭据复用接口 | 在副作用前验证全部目标及归属；禁止跨父对象混用，即使两个项目均可访问 |
| C/O 并发重复授权、重复取消、授权跨组织用户 | 唯一成员行、幂等结果、无跨组织身份泄露；隐式管理身份不可通过成员接口取消 |
| 普通用户通过草稿项目、导入或替代入口尝试新建项目 | 被拒绝；仅有效组织负责人可创建，归属由服务器固定 |
| 禁用 A 后继续使用已打开页面、Token、SDK | 后续鉴权拒绝；历史标注保留；页面不误报保存成功 |
| A 被移出组织、重新加入、切换 active organization 或账号暂停 | 组织边界始终生效；重新加入不恢复旧显式项目成员行 |
| 请求上传图、本地文件、云解析、签名 URL 和导出文件 | 新授权检查一致；覆盖独立 Nginx 导出鉴权及存储前缀边界 |
| 普通账号持有遗留 staff/superuser 标志 | 不能凭标志绕过应用 ACL 或通过 Django admin 获取未授权项目 |
| 旧数据存在重复、禁用成员和空创建者 | 迁移结果确定；仅管理者可见旧项目，重复升级不再次禁用已确认授权 |

后端使用仓库现有 pytest/Tavern 设施验证 API 与数据迁移，SQLite 和 PostgreSQL 均覆盖唯一约束与查询语义；补充真实浏览器端到端用例，验证管理者授权、普通成员标注、禁止操作和撤销后的保存反馈。文件代理/Nginx 路径按实际部署方式验收；云签名过期行为使用受控测试对象验证。[R1]

本次 spec 提交只验证文档完整性、规则一致性、Markdown 结构及远端保存结果；上表是后续实现的验收要求，不代表已执行或通过功能测试。

## 12. 实现边界与审阅重点

新增代码集中在项目权限与成员 API 小模块，现有资源入口做必要接入；避免重写标注编辑器、任务调度或组织模型。成员页面沿用现有组件与设计系统，权限响应保持只读。

实现计划必须列出外部入口到权限规则的覆盖清单，尤其是列表、批量操作、文件响应和可能提前触发副作用的 serializer；不能用“全局权限类已接入”代替逐类验证。具体编码任务和提交拆分在本文审阅确认后形成。

文档审阅重点为：组织负责人统一创建项目；成员可看所有已提交标注但仅改本人结果；草稿仅本人可见；隐式管理身份不能通过取消成员撤销；首次迁移清空历史显式授权并按确认名单重授；文件隔离采用项目存储目录/prefix 边界。
